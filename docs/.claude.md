# Instruções para Claude - Parle Backend

Este arquivo fornece contexto essencial sobre o projeto Parle Backend para melhorar a assistência do Claude AI durante o desenvolvimento.

## 📋 Visão Geral do Projeto

**Parle Backend** é uma plataforma completa de conversação speech-to-speech com arquitetura monolítica modular. O sistema processa áudio de entrada, transcreve para texto, gera respostas usando modelos de linguagem e converte de volta para áudio.

### Características Principais
- 🎤 **Speech-to-Speech Completo**: Pipeline end-to-end de áudio para áudio
- 🏗️ **Arquitetura Monolítica Modular**: Todos os serviços em um único processo com módulos internos
- 🔄 **Tempo Real**: Suporte a WebSocket (processo separado) e WebRTC
- 🤖 **IA Integrada**: STT (Whisper), LLM (GPT-2/LiteLLM), TTS (ElevenLabs/HuggingFace)
- 🎓 **Intelligent Tutoring System (ITS)**: Sistema completo de tutoria adaptativa com AKT, SINKT, e análise CEFR
- ⚡ **Performance**: Chamadas diretas Python entre módulos (sem overhead HTTP)

### Modo de Operação

- **Monolito Modular** (padrão): Todos os módulos rodam no mesmo processo Python
- **Chamadas Diretas**: Comunicação entre módulos via chamadas Python (sem HTTP)
- **WebSocket Separado**: Processo isolado que comunica com API via HTTP (localhost:8000)

### Módulos Principais

#### Módulos de IA
- **STT** (`src/modules/speech/stt/`): Speech-to-Text (Whisper, Groq)
- **LLM** (`src/modules/llm/`): Language Model (GPT-2, LiteLLM, múltiplos provedores)
- **TTS** (`src/modules/speech/tts/`): Text-to-Speech (ElevenLabs, HuggingFace)
- **Neural Codec** (`src/modules/speech/neural_codec/`): Codec neural para compressão

#### Módulos de Conversação
- **Orchestrator** (`src/modules/conversation/orchestrator/`): Orquestrador central do pipeline
- **Session** (`src/modules/conversation/session/`): Gerenciamento de sessões
- **Scenarios** (`src/modules/conversation/scenarios/`): Gerenciamento de cenários

#### Módulos de Armazenamento
- **Conversation History** (`src/modules/storage/conversation_history/`): Histórico de conversações
- **Conversation Store** (`src/modules/storage/conversation_store/`): Armazenamento estruturado
- **Database** (`src/modules/storage/database/`): Banco de dados genérico
- **File Storage** (`src/modules/storage/file_storage/`): Armazenamento de arquivos

#### Módulos de Tutoria Inteligente (ITS)
- **Student Model** (`src/modules/tutoring/student_model/`): AKT (Attentive Knowledge Tracing) com IRT
- **Diagnostic** (`src/modules/tutoring/diagnostic/`): Análise de erros e SINKT
- **Pedagogical Policy** (`src/modules/tutoring/pedagogical_policy/`): Engine de política pedagógica
- **Learning Path** (`src/modules/tutoring/learning_path/`): Navegação de caminhos de aprendizado

## 💻 Padrões de Código e Convenções

### Estrutura de Módulos

```python

    """Descrição do módulo"""
    
    async def initialize(self):
        """Inicialização do módulo"""
```

### Configuração

- **Configuração Unificada**: `src/core/config.py` centraliza todas as configurações
- **Variáveis de Ambiente**: Usar prefixos específicos (ex: `LLM_`, `STT_`, `TTS_`)

### Logging

- **Biblioteca**: Usar `loguru` em todos os serviços
- **Formato**: Logs enviados para `stdout`/`stderr` (capturados pelo Nomad)
- **Níveis**: `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`

```python

logger.info("Mensagem informativa")
logger.error("Erro ocorreu", exc_info=True)
```

### Tratamento de Erros

- **Exceções Customizadas**: Usar exceções específicas do projeto quando apropriado
- **Logging**: Sempre logar erros com contexto completo
- **Fallbacks**: Implementar fallbacks para serviços externos (ex: LLM, STT, TTS)

### Type Hints

- **Sempre usar type hints**: Facilitar manutenção e detecção de erros
- **Pydantic Models**: Usar para validação de dados de entrada/saída

## ⚠️ Warnings e Pitfalls

### ⚠️ Arquivos Temporários / Gerados por IA

**IMPORTANTE**: Todos os arquivos temporários gerados por IA (markdown, texto, JSON, relatórios, notas, scripts auxiliares, etc.) devem ser escritos dentro do diretório `tmp/` na raiz do projeto, **NÃO** na raiz do projeto.

#### Exemplos de arquivos que devem ir em `tmp/`:
- `MIGRATION_STATUS.md`
- `IMPLEMENTATION_COMPLETE.md`
- `TEST_RESULTS.md`
- `FIXES_APPLIED.md`
- `CLEANUP_SUMMARY.md`
- `NEXT_STEPS_*.md`
- `SERVICES_*.md`
- Qualquer arquivo temporário de documentação ou experimento gerado pela IA

#### Arquivos que devem permanecer na raiz:
- `README.md` (documentação principal do projeto)
- Arquivos markdown em `docs/` (documentação permanente)
- Arquivos markdown em subdiretórios específicos (como `tests/e2e/README_*.md`)

**Motivo**: Manter a raiz do projeto limpa e organizada, facilitando a navegação e evitando acúmulo de arquivos temporários gerados automaticamente.

### ⚠️ Modo Monolith vs Microservices

- **Nunca usar serviços HTTP** em modo monolith - usar módulos diretamente
- **Verificar `MONOLITH_MODE`**: Sempre verificar se está em modo monolith antes de fazer chamadas HTTP internas
- **Módulos vs Serviços**: `src/modules/` é para monolith, `src/services/` é legacy

### ⚠️ Dependências

- **Conda é o padrão**: O projeto usa Conda, não venv/pip isolado
- **Python 3.11+**: Garantir compatibilidade com Python 3.11
- **Submódulos**: Verificar se submódulos estão atualizados (`git submodule update`)

### ⚠️ Banco de Dados

- **SQLite por padrão**: Desenvolvimento local usa SQLite (`./data/parle.db`)
- **Migrations**: Verificar se há migrations pendentes antes de mudanças no schema
- **Backup**: Sempre fazer backup antes de mudanças estruturais

### ⚠️ ITS (Intelligent Tutoring System)

- **Skills CEFR**: Skills são filtradas por nível CEFR do aluno (não enviar skills avançadas para iniciantes)
- **AKT Parameters**: Não alterar parâmetros do AKT sem validação estatística
- **SINKT**: SINKT usa LLM - considerar custo e latência
- **Historical Data**: Análise de padrões usa últimos 90 dias - considerar performance

## 🎯 Diretrizes de Desenvolvimento

### Ao Adicionar Novos Módulos

1. Criar estrutura em `src/modules/<module_name>/`
2. Implementar `BaseModule` ou classe similar
3. Registrar no `src/api/main.py` (função `initialize_modules()`)
4. Adicionar configuração em `src/core/config.py` se necessário
5. Criar testes E2E em `tests/e2e/`
6. Documentar em `docs/`

### Ao Modificar APIs

1. Atualizar rotas em `src/api/routers/`
2. Atualizar documentação OpenAPI (gerada automaticamente pelo FastAPI)
3. Adicionar/atualizar testes E2E
4. Verificar compatibilidade com frontend

### Ao Trabalhar com ITS

1. Entender o fluxo completo: Diagnostic → Student Model → Pedagogical Policy → LLM
2. Considerar impacto em performance (LLM calls)
3. Validar com dados reais antes de deploy
4. Documentar mudanças em parâmetros de modelos (AKT, IRT, etc.)
